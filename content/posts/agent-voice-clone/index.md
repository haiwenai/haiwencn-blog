段永平的《大道》，509页，33万字。我断断续续读了两个月，还卡在第二章。

不是不想读。是生活不给你整块时间。拿起书读三页，女儿喊你，放下。第二天翻开，忘了昨天读到哪，再从上一节开始。读了两个月，进度条几乎没动。

那天下午去接女儿放学，开车走到半路，脑子里突然冒出一个想法：如果能用一个我喜欢的声音，把这本书读给我听呢？

不是喜马拉雅上找一个播音员录好的版本。是**我指定的声音**，读**我指定的内容**。开车时听，做饭时听，带孩子去公园时挂个耳机听。阅读的瓶颈不是眼睛，是场景——而耳朵能到达眼睛去不了的地方。

这个想法从冒出来到落地，大约十分钟。

不是十分钟"想清楚"，而是十分钟"跑通"。回到家，打开 Mac mini，跟我的 AI agent 说了这个需求，它从评估方案到写完代码到第一个音频文件生成，十分钟。整本书33万字的完整有声书，五个小时后全部生成完毕。138个章节，每章一个音频文件，配一份对应的原文，在 Obsidian 里排得整整齐齐。点开播放，是我自己克隆的声音在读段永平谈投资。

从一个开车时的念头，到一整条生产管道跑通。中间没有任何人工介入。

这件事本身不值得写一篇文章。值得写的是它背后的东西。

---

## 一个想法是怎么变成一条管道的

先说清楚到底发生了什么。

一本 PDF 书，对计算机来说就是一堆带格式的字节。把它交给 PyMuPDF，逐页提取出纯文本。但提取出来的文本不能直接用——PDF 的排版会制造大量噪音：一个词在页面上被换行切成两半（"极\n小"变成"极"和"小"两个独立的字），页眉页脚混在正文里，章节标题和正文黏在一起。

这些噪音人眼能自动过滤，但语音合成引擎不会。它会老老实实地在"极"和"小"之间停顿一下，听起来像结巴。所以第一步不是合成语音，而是清洗文本：合并被排版打断的段落，去掉页眉页脚，识别出哪些行是章节标题、哪些是正文。

清洗完，要切分。一本33万字的书不能扔给语音引擎一口气念完。要按章节切，每章再按合适的长度切成更小的块，每块几百字，语音引擎逐块合成。合成完的音频碎片再用 ffmpeg 按顺序拼回完整章节。

最后是输出。不是扔一堆 mp3 文件在桌面上就完事。每个章节一个音频文件，配一个 markdown 文件放原文，两者成对放在 Obsidian 的目录下。打开 Obsidian，点开某一章，上面是播放器，下面是原文，可以边听边看。就像你在听一个人读书，同时手边摊着那本书。

整条管道：PDF → 文本提取 → 清洗 → 章节切分 → 语音合成 → 音频合并 → 配对输出。

听起来步骤很多，但每一步都不是什么新技术。文本提取有 PyMuPDF，语音合成有 Edge TTS 和各种克隆语音API，音频处理有 ffmpeg，文件组织有脚本。这些轮子早就在那里了。以前做不到的不是任何一个单项能力，而是把它们串起来。

串起来这件事，以前需要一个程序员花几天写代码调试。现在 AI agent 能做。

## 具体怎么串的

我用的是 [OpenClaw](https://github.com/openclaw/openclaw)，一个开源的 AI agent 框架。它跑在我的 Mac mini 上，24小时在线，我通过飞书跟它对话就行。

OpenClaw 有一个 skill 机制——你可以给 agent 写"技能"，每个技能是一组代码和规则，agent 需要的时候自动调用。我做的事情是：跟 agent 描述我想要什么，它帮我写了一个叫 `pdf-to-audiobook` 的 skill。

这个 skill 做的就是上面那条管道。但有几个关键决策值得说。

**语音引擎的选择。** 我测了两个方案。一个是微软的 Edge TTS，免费，中文音色十几种，合成速度快，质量中规中矩——听起来像一个标准的AI播音员在读稿，字正腔圆但没感情。另一个是 Noiz，一个语音克隆平台，我上传了几分钟自己的录音，它给我一个API接口，以后给它任何文本，返回的都是我的声音。

Edge TTS 的好处是快，33万字几十分钟能跑完。Noiz 的好处是真实，但慢——每500字要调一次API，每次大约50-80秒，全书估算要10-12个小时。

最后决定两个都留。Edge 做快速试听和调试，Noiz 做正式版。在 skill 里加了 `--engine` 参数，一行命令切换。

**章节识别的坑。** 最初的方案是用正则匹配章节标题——"第X章"、"第X节"之类的模式。听起来简单，但《大道》这本书的章节结构很不规整，有的地方用"第一章"，有的地方用"1."，有的地方就是一个加粗的标题。更要命的是 PDF 提取偶尔会丢字，比如"第二章"提取出来变成了"第 章"——中间的"二"不知道去哪了，正则直接匹配失败。

最后的方案是：不完全依赖正则。先从 PDF 的目录页（这本书有9页目录）提取出所有章节和小节标题，做成一个 JSON 文件，然后按这个目录去正文里定位每个小节的起止位置。这样即使某个标题被OCR搞坏了，也能通过上下文找到大致位置。

177个目录标题，最终稳定切出138个独立段落，每段1000到15000字不等。

**断行的教训。** 第一版生成的音频发给自己试听，发现有些地方莫名其妙地停顿。排查后发现是 PDF 提取的断行问题——原文中"极小"这个词在 PDF 排版中恰好被分在两行，提取出来变成了"极\n小"，语音引擎忠实地在两个字之间加了停顿。

修的办法不复杂：在清洗阶段加一个逻辑，判断一个换行是排版导致的（上一行没有句号/问号/感叹号结尾）还是真正的段落分隔。前者合并，后者保留。但如果不是自己真的去听了那段音频，这个问题可能永远不会被发现。

**最终的命令大概长这样：**

```bash
python3 pdf_to_audiobook.py \
  --pdf "大道_段永平投资问答录.pdf" \
  --engine noiz \
  --start-page 22 \
  --toc dadao_toc.json \
  --obsidian \
  --output ~/Obsidian/有声书/大道/
```

一行命令。PDF 从这头进去，有声书从那头出来。跑了一晚上，早上起来，138个章节整整齐齐地在 Obsidian 里等着。

## Obsidian 里的样子

打开 Obsidian，左侧目录树展开"有声书/大道"，138个文件按章节排列：

```
有声书/大道/
├── 目录.md
├── 001_投资大道.md
├── 001_投资大道.mp3
├── 002_买股票就是买公司.md
├── 002_买股票就是买公司.mp3
├── ...
├── 138_后记.md
└── 138_后记.mp3
```

点开任意一章，上半部分是嵌入的音频播放器，点击就能播放。下面是这一章的完整原文。在手机上也一样——Obsidian 移动端支持音频嵌入，走路的时候打开就能边听边看。

这不是一个"听书"应用，是我自己的知识库里多了一个维度。同一本书，可以用眼睛读，可以用耳朵听，可以在笔记旁边标注，可以全文搜索。所有内容都在本地，没有平台锁定，没有会员到期。

## 不只是一本书

管道搭好之后，我很快意识到：输入端不一定是 PDF。

任何能变成文本的东西，都能进这条管道。一篇公众号长文，抓下来就是文本。一个 YouTube 视频，提取字幕就是文本。一份研究报告、一组会议纪要、一本 epub 电子书——形式不同，但最终都能归约成纯文本，然后进入同一条管道，出来就是指定声音的音频。

输出端也不一定是 Obsidian。可以是按章节切好的 mp3 扔到手机里当播客听。可以是一条一条的语音消息发到飞书群里。可以是嵌入到 Notion 或者任何支持音频的笔记工具里。

声音也不一定是我的。

这是后来才想明白的。Noiz 的声音克隆不限于自己——任何人上传几分钟录音，都能生成一个专属的声音模型。这意味着三个变量完全自由：

**用谁的声音。** 你自己的，你伴侣的，你导师的，你喜欢的某个播客主播的。

**读什么内容。** 一本冷门的投资书，一份只有你关心的行业报告，你孩子学校发的课外阅读材料，你自己写的日记。

**在哪里听。** 开车、跑步、做饭、睡前、通勤地铁上。

把这三个变量拼起来，能拼出远超"有声书"这个词能装得下的组合——

一个妈妈经常出差。她录了几分钟自己的声音，以后想给孩子讲的绘本、想读的故事，丢进去就行。孩子听到的不是机器音，是妈妈的声音。妈妈不在的晚上，声音在。

一个老师把这学期的重点讲义变成自己声音的音频。学生期末复习的时候，塞上耳机听到的是课堂上那个熟悉的声音在讲同样的内容。熟悉感降低认知负荷这件事，心理学已经研究了几十年。

一个人深夜睡不着，想听到某个已经不在身边的人的声音念一段话给自己。

这些场景没有一个是"有声书行业"会去服务的。因为它们太个人、太零散、太不标准化。一个出版社不可能为每个妈妈单独录一版有声书。一个音频平台不可能为每个学生匹配他自己老师的声音。

但一条本地管道可以。因为它的边际成本几乎是零。

## 编译器来了，然后呢

这整件事最让我在意的不是技术。

是"十分钟"这个数字。

从"我想用自己的声音读这本书"到一条完整管道跑通——评估方案、选引擎、写代码、测试、修 bug、正式运行——十分钟。这里面真正需要人类（也就是我）参与的部分是什么？

一个想法。一个开车时冒出来的念头。

剩下的全是执行。评估哪个语音引擎好用是执行，写 Python 脚本是执行，调 ffmpeg 参数是执行，排查断行 bug 是执行。这些事情每一件单拆出来都需要专业能力——但这些能力现在不稀缺了。

这像什么？像编译器出现之前和之后。

编译器出现之前，你有一个程序的想法，要自己写汇编。写汇编不是不能做，但它要求你同时在两个层面思考：一层是你要解决的问题本身，一层是机器怎么执行。绝大部分精力花在第二层。

编译器出现之后，你只管写高级语言，编译器替你翻译成机器码。你不需要知道寄存器怎么分配，不需要知道指令怎么流水线化。你只管写你的逻辑。

但编译器不会替你写程序。

它降低了"执行"的门槛，但没有降低"想清楚要做什么"的门槛。相反，当所有人都有编译器了，"想清楚要做什么"变成了唯一的竞争力。

AI 现在对所有人做的事情，和编译器对程序员做的事情，结构上一模一样。

它把执行力拉平了。以前你想做一个有声书，需要找录音棚、找播音员、找后期团队、找发行渠道。这些执行环节构成了巨大的壁垒——成本壁垒、技能壁垒、资源壁垒。只有头部内容值得做，长尾需求不经济。

现在这些壁垒在塌陷。不是慢慢降低，是按数量级在坍缩。一个人、一台电脑、一个想法，能撬动以前需要一个团队才能完成的产出。

但"一个想法"这件事，AI 做不了。

它能帮你实现任何想法，但它不会在开车接孩子的路上突然冒出"我想用自己的声音读那本书"这个念头。它不会在洗澡的时候想到两个不相关的事情之间的联系。它不会因为对某件事感到不爽而产生"我要把这个搞定"的冲动。

想法来自于你独特的生活经历、你的品味、你的不满、你的好奇心。这些东西目前为止还没有被拉平，我觉得相当长的时间内也不会。

所以如果你问我"AI 时代最重要的能力是什么"，我的回答不是"学会用 AI 工具"——那是执行层面的事，门槛会越来越低。最重要的能力是：持续产生值得执行的想法。

知道自己想要什么。知道什么东西应该存在但还不存在。知道一个不合理的现状可以被怎样改变。

工具越强大，方向感越值钱。编译器时代如此，AI 时代也如此。

## 一条还在跑的管道

写这篇文章的时候，那条管道还在我的 Mac mini 上安静地跑着。

138个章节，大概跑了五个多小时。Noiz 的API一块一块地把文本变成我的声音，ffmpeg 一章一章地把碎片拼成完整的音频，脚本一对一对地把音频和原文写进 Obsidian。

明天开车的时候，我会打开 AirPods，从第一章开始听段永平谈投资。用的是我自己的声音。在两个月都啃不动的那本书和一个下午跑通的管道之间，真正的距离不是技术，不是工具，不是代码。

是那个接女儿路上冒出来的念头。
